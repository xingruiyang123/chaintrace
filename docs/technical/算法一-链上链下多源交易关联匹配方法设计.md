# 算法一：面向涉虚拟货币案件的链上链下多源交易关联匹配方法设计

## 1. 研究问题

给定同一案件中的：

- 链上转账事件；
- 交易平台充币、提币或内部记账事件；
- 供述、聊天记录、报告等案件材料中抽取的结构化主张；
- 账户、资产、时间和来源信息；

在金额存在手续费或四舍五入偏差、时间记录不完全一致、账户标识不完整、来源之间可能冲突的情况下，生成**可解释、可复核的候选对应关系**。

算法不直接认定钱包归属、不直接认定人员身份，也不把匹配分数解释成概率。最终结果写入 `candidate_match`，由人工复核后再形成案件关系或线索。

## 2. 输入与输出契约

### 2.1 输入

| 输入 | 数据表 | 关键字段 |
|---|---|---|
| 标准化资金事件 | `money_event` | `event_type`、`asset_id`、`amount`、`event_time`、账户、交易哈希/业务编号 |
| 案件主张 | `claim` | 主体节点、谓词、客体节点、资产、金额、时间范围、证据 |
| 账户节点 | `entity_node`、`financial_account` | 节点类型、账户类型、网络命名空间 |
| 来源记录 | `source_record`、`money_event_source_record` | 原始记录、来源可靠度、模拟标记、哈希 |
| 案件范围 | `investigation_case` | 案件编号和数据权限边界 |

### 2.2 输出

每个候选结果至少包含：

- `left_node_id`：资金事件节点；
- `right_node_id`：主张节点；
- `match_type='EVENT_TO_CLAIM'`；
- `score`：用于排序的解释性分数；
- `explanation`：各维度命中情况、容差和来源；
- `missing_items`：字段缺失；
- `conflict_items`：明确冲突；
- `review_status='PENDING'`。

算法运行写入 `analysis_run`，输入快照、参数和版本必须可复现。

## 3. 先做语义分离，再做关联

链上转账和交易平台内部入账是两个独立的 `money_event`：

```text
链上地址 A --ONCHAIN_TRANSFER--> 平台充值地址 C-TRON
平台账户 C-EXCHANGE --EXCHANGE_DEPOSIT--> 平台内部账户
```

二者只有在交易哈希、平台订单号、金额、时间、账户映射和其他材料共同支持时，才建立 `RECONCILES_WITH` 候选关系。算法一的事件—主张匹配不会把两个会计事件自动合并。

## 4. 规范化处理

### 4.1 金额

对每条事件和主张生成：

```text
amount_raw
amount_decimal
amount_abs_delta = |event.amount - claim.amount|
amount_rel_delta = amount_abs_delta / max(|event.amount|, ε)
```

金额比较使用：

```text
amount_match =
    1.0                         if amount_abs_delta <= abs_tol
    1 - amount_rel_delta        if amount_rel_delta <= rel_tol
    0.0                         otherwise
```

`abs_tol` 和 `rel_tol` 必须写入 `analysis_run.parameters`。稳定币、原生币和不同精度资产不能共用未经说明的容差。

### 4.2 时间

统一转为 UTC，并保存原始时区信息。为事件和主张计算：

```text
time_delta_seconds = |event_time - claim_time|
time_match = max(0, 1 - time_delta_seconds / time_window_seconds)
```

若主张只有时间范围，则判断事件时间是否落在范围内；若没有时间，记为缺失，不记为冲突。

### 4.3 方向与账户

将主张谓词映射为方向约束：

| 主张谓词 | 方向要求 |
|---|---|
| `PAID_TO` | 事件转出账户对应主体，接收账户对应客体 |
| `RECEIVED_FROM` | 与 `PAID_TO` 相反 |
| `TRANSFERRED_TO` | 允许主体/客体为账户节点 |
| `CONTROLLED` | 不作为资金事件匹配的方向条件，只作为身份主张 |

账户匹配优先级：

1. 同一账户节点或同一规范化标识；
2. 同一命名空间下的账户标识；
3. 已审核的 `CONTROLS/USES` 关系；
4. 只有人员名称或自由文本时，不视为账户命中。

### 4.4 资产与来源

- `asset_id` 相同是强条件；
- 仅 symbol 相同但网络不同，记为冲突或信息不足，不能直接命中；
- `source_record.raw_sha256` 必须通过校验；
- 模拟来源保留 `is_simulated=true`，不得在结果中被描述为真实证据。

## 5. 两阶段匹配流程

### 5.1 阶段一：候选生成

避免事件与主张全量笛卡尔积。按以下条件生成候选集：

1. 同一 `case_id`；
2. 资产相同，或属于显式配置的可转换资产组；
3. 时间差不超过配置窗口；
4. 金额落在绝对/相对容差内，或至少存在一项可比金额；
5. 账户方向没有硬冲突。

建议索引：

- `money_event(case_id, asset_id, event_time)`；
- `claim(case_id, asset_id, event_time_from, event_time_to)`；
- `money_event(case_id, tx_hash)`；
- `source_record(case_id, external_record_id)`。

### 5.2 阶段二：可解释评分

基础权重建议先固定为规则参数，不训练模型：

| 维度 | 权重 | 说明 |
|---|---:|---|
| 外部唯一标识 | 0.35 | 交易哈希、平台订单号等精确对应 |
| 资产与网络 | 0.20 | `asset_id`、网络命名空间一致 |
| 金额 | 0.20 | 容差内的金额接近度 |
| 时间 | 0.15 | 时间差越小分数越高 |
| 方向与账户 | 0.10 | 主体、客体、账户方向一致 |

```text
score = Σ(weight_i × feature_i)
```

规则：

- 存在唯一标识精确命中且无硬冲突：`EXACT`；
- `score >= 0.75` 且无硬冲突：`CANDIDATE_STRONG`；
- `0.55 <= score < 0.75`：`CANDIDATE_REVIEW`；
- 存在明确资产、方向、时间或唯一标识冲突：`CONFLICT`；
- 可比字段过少：`INSUFFICIENT`。

这些等级写入 `explanation.match_class`，不替代 `review_status`。

## 6. 缺失与冲突处理

### 6.1 缺失

缺失字段包括：

- 只有金额，没有时间；
- 只有时间范围，没有具体时间；
- 账户未能规范化；
- 主张没有交易哈希或订单号。

缺失不扣成“反向证据”，写入 `missing_items`，并保留其他维度的排序分。

### 6.2 冲突

冲突字段包括：

- 交易哈希对应的资产与主张资产不同；
- 方向相反且谓词不允许反向；
- 时间差超过硬窗口；
- 同一订单号对应两个不相容金额；
- 来源哈希校验失败。

有硬冲突时不得自动生成 `ACCEPTED` 关系，只能生成 `review_status='DISPUTED'` 或不生成候选。

## 7. 伪代码

```text
for each case:
    events = load_money_events(case)
    claims = load_claims(case)
    snapshot = hash(events, claims, source_versions, parameters)
    run = create_analysis_run(snapshot)

    for event in events:
        candidates = retrieve_by_case_asset_time_amount(event, claims, parameters)

        for claim in candidates:
            features = compare(event, claim, parameters)
            if features.hard_conflicts:
                save_candidate(run, event, claim,
                               class="CONFLICT",
                               missing=features.missing,
                               conflicts=features.hard_conflicts)
                continue

            score = weighted_score(features)
            match_class = classify(score, features)
            save_candidate(run, event, claim,
                           class=match_class,
                           score=score,
                           explanation=features,
                           missing=features.missing,
                           conflicts=[])
```

## 8. 实验设计

### 8.1 数据集

分成两套，禁止混合统计：

1. **公开事实集**：只录入公开披露的人员、账户代号、关系和来源，不补造未公开的哈希、金额和时间。
2. **模拟交易集**：人工生成带真值标签的事件—主张对应关系，覆盖金额偏差、时间偏差、重复导入、缺字段和冲突来源。

模拟来源全部标记 `is_simulated=true`。

### 8.2 最小实验组

| 实验 | 场景 | 预期验证 |
|---|---|---|
| A01 | 交易哈希精确命中 | `EXACT` 能否稳定识别 |
| A02 | 金额存在手续费偏差 | 容差规则是否保留候选 |
| A03 | 时间相差数小时 | 时间窗口是否合理排序 |
| A04 | 资产相同但网络不同 | 是否正确拒配 |
| A05 | 链上事件与平台入账分开 | 是否保持两个事件并建立候选核对 |
| A06 | 一个事件多个来源 | 是否不重复计入事件 |
| A07 | 重复导入相同链上事件 | 幂等索引是否拦截 |
| A08 | 缺少时间或账户 | 是否进入 `missing_items` |
| A09 | 金额、方向或哈希冲突 | 是否进入 `CONFLICT/DISPUTED` |
| A10 | 模拟数据混入报告 | 导出层是否保留模拟标识 |

### 8.3 评价指标

| 指标 | 定义 |
|---|---|
| Precision@1 / @5 | 前 1/5 个候选中正确对应的比例 |
| Recall@K | 真值对应是否出现在前 K 个候选中 |
| 错误关联率 | 被人工判定为错误的候选占比 |
| 冲突拦截率 | 已标注冲突被正确拦截的比例 |
| 重复导入拦截率 | 重复事件被唯一约束拒绝的比例 |
| 候选压缩率 | 候选数相对全量组合数的下降比例 |
| 人工复核耗时 | 与人工逐条比对的耗时对照 |

首轮验收重点是错误关联率、冲突拦截率和候选压缩率，不以单纯提高召回率为目标。

## 9. 与数据库的对应关系

| 算法步骤 | 落库位置 |
|---|---|
| 输入快照 | `analysis_run.input_snapshot_hash`、`parameters` |
| 候选事件—主张对 | `candidate_match.left_node_id/right_node_id` |
| 匹配类别和分数 | `candidate_match.match_type/score/explanation` |
| 缺失与冲突 | `candidate_match.missing_items/conflict_items` |
| 人工复核 | `candidate_match.review_status/reviewer_id/reviewed_at` |
| 证据支撑 | `relation_evidence`、`clue_basis` |
| 跨事件核对 | `investigative_relation.relation_type='RECONCILES_WITH'` |

## 10. 研发顺序

1. 先实现规则版规范化与候选生成；
2. 用 A01–A05 验证匹配规则和阈值；
3. 加入 A06–A09 的多来源、重复和冲突处理；
4. 冻结 `candidate_match` 输出契约；
5. 再评估是否需要统计学习或图算法，不能在没有真值数据前直接训练“钱包归属模型”。
